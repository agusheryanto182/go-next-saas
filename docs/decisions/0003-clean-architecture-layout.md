# 0003. Clean architecture with the go-clean-template layout

- **Status:** Accepted
- **Date:** 2026-11-23

## Context
The API will grow over many domains and much of it will be written by coding agents. Without enforced boundaries, HTTP details leak into business logic and queries spread everywhere.

[evrone/go-clean-template](https://github.com/evrone/go-clean-template) is a widely used, maintained layout for clean architecture in Go. Its libraries (Fiber, Squirrel, Swaggo, JWT, message brokers) do not match our other decisions.

## Decision
Follow the template's **layout and rules**, without cloning it:

```
api/
├─ cmd/app/                  entry point
├─ config/                   environment configuration
├─ internal/app/             wiring (manual DI), start and shutdown
├─ internal/controller/restapi/{middleware,v1}
├─ internal/entity/          business models
├─ internal/usecase/         contracts.go + one folder per domain
├─ internal/repo/            contracts.go + persistent/ (PostgreSQL) + webapi/ (SMTP and other services)
└─ pkg/                      generic infrastructure, no business logic
```

Rules:
- Dependencies point inward: controller → usecase → repo. Use cases import only the standard library, `entity` and contracts (plus `google/uuid` to create IDs, and OpenTelemetry in `tracing.go`).
- Layers talk through interfaces in `contracts.go`; dependencies are passed through constructors.
- Data crosses layers as `entity` types.
- Layer direction is enforced by `depguard` in golangci-lint, so a violation fails CI.

### Template conventions adopted (2026-11-25)
An audit against the template's current source aligned the code with its conventions, not only its folders:
- One package per domain per layer: `usecase/<domain>/`, `repo/persistent/<domain>/`. Constructors are `New`, take dependencies as arguments and return the contract interface wrapped in a tracing decorator (`tracing.go`, OpenTelemetry spans; attributes carry IDs, never personal data).
- Domain errors are sentinels in `entity/errors.go`; other errors are wrapped with the layer path (`"OrganizationRepo - Store - q.CreateOrganization: %w"`). Only controllers map sentinels to HTTP.
- Entity IDs are UUID strings, so `entity` stays standard-library only; repositories parse them.
- Mocks are generated by mockgen from `//go:generate` lines in both `contracts.go` files into `usecase/mocks_*_test.go`; use-case tests use testify and gomock and run in parallel.
- The template's correctness and consistency linters (`err113`, `exhaustive`, `gochecknoglobals`, `paralleltest`, `cyclop`, …) are enabled; its style-only ones (`wsl`, `nlreturn`, `mnd`, `funlen`, `godot`) are not.
- `api/AGENTS.md` follows the template's agent guide: where code goes, the handler contract, and checklists for a new use case or domain.

Kept from our own decisions: `net/http` (0004), the generated strict server instead of hand-written DTOs (0005), sqlc and goose (0009), `log/slog`, a validated `config`, `app.Run` returning errors instead of `log.Fatal` (deferred cleanup runs), and migrations as a separate owner-role step (0008). Attribution: `api/NOTICE`.

### Deviation: unit of work
The template has no transactions; each repository method uses the pool. Row-level security (ADR 0008) needs every query inside a transaction that sets the scope, so `repo/contracts.go` adds one interface:

```go
Transactor interface {
    InScope(ctx context.Context, scope Scope, fn func(ctx context.Context) error) error
}
```

Use cases keep the template's shape (repositories injected through `New`) and call repositories with the `ctx` that `fn` receives. Repositories take the transaction from that `ctx` and return `ErrNoUnitOfWork` without one: there is no fallback to the pool, so a forgotten `InScope` fails the first test instead of running a query without a scope. `InScope` calls do not nest. Considered instead: passing a bundle of transaction-bound repositories to `fn`, which catches the mistake at compile time but departs further from the template's use-case shape.

## Alternatives considered
- **Package by feature (as in employee-portal):** fine for a small app; less explicit boundaries as domains multiply.
- **Clone the template:** most of its libraries would be removed again, leaving leftovers that confuse agents.
- **Flat `internal/` packages:** simplest, but no protection against layer leaks.

## Consequences
- Business logic is unit-testable with mocks (`go.uber.org/mock`).
- More files and interfaces than a flat layout; the template's own advice applies: add layers only when needed.
- A contract method is written three times (interface, implementation, tracing decorator); the compiler catches a missing one.
- Code follows a widely used reference closely, which makes it predictable for people and coding agents.
